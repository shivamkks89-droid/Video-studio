# RCA — "Render failed — Render 2 baar try karke bhi poora nahi hua" (video-studio-ai-38)

**Run:** b495224f-8c5f-409a-916f-d092df3d5839 (active, tier_0 Starter, cloudflare frontend)
**Reported:** ~19:49 IST / 14:19 UTC, 5 Nov. Push: "Render 2 baar try karke bhi poora nahi hua".

## Exact cause (two compounding faults)

### 1. Backend pod is OOMKilled mid-render at the tier_0 512Mi memory limit
`get_pod_events` (container `...-qsr84`):
- `last_termination: OOMKilled, exit_code 137, finished_at 2026-11-05T14:01:04Z, restarts=2`
- Both replicas (`qsr84`, `hpkpz`) show repeated 503 / `connection refused` on `/health`, `BackOff restarting`, CrashLoopBackOff.

`get_tier`: tier_0 memory request **200Mi**, **limit 512Mi**, **replicas 2 (max 2)**. The ffmpeg/imageio video render exceeds 512Mi → kernel OOM-kills the container (exit 137). All three failed `render_jobs` are frozen at **progress: 49** — i.e. killed partway through the render, not a logic failure.

### 2. `attempts` is inflated past 2 by multi-instance + restart re-increments (false "2 tries" message)
- `entrypoint.sh` starts a single `uvicorn server:app` (no `--workers`) → **1 uvicorn worker per pod**, but the tier runs **2 replicas**, so `resume_render_jobs()` runs **once per pod = twice per backend "generation"**, each with its own semaphore.
- Every OOM restart boots the pod again → `resume_render_jobs()` fires again and `$inc`s `attempts` for any pending/rendering job.
- `fetch_app_logs` proves the multiplication:
  - `[render] resuming job_f49e851b7f2b after restart ×2`
  - `[render] resuming job_8226be75b458 after restart` (logged **twice**)
  - `[render] resuming job_95b0f3970560 after restart` (logged **twice**)
- `render_jobs` docs: the three recent jobs (job_95b0f3970560 @13:50, job_f49e851b7f2b @13:59, job_8226be75b458 @14:02 UTC) all have **attempts: 3**, `status: failed`, `refunded: true`, error = "Render 2 baar try karke bhi poora nahi hua…".

## Causal chain
Memory-heavy render → pod OOMKilled (exit 137) at 512Mi mid-render (progress 49) → pod restarts → **both replicas** run `resume_render_jobs()` and re-`$inc` `attempts` on every boot → `attempts` jumps past 2 well before the user has had two genuine completed attempts → `_queued_render()` sees `attempts > 2`, emits the "2 baar try…" failure + refund. The user-facing "2 tries" message is therefore misleading: the real failure is the **OOMKill**, and the attempts counter is **inflated by the 2-replica resume + restart re-increments**.

3. **Concurrency:** 1 uvicorn worker per pod (entrypoint has no `--workers`), but **2 replicas** (tier replicas=2/max=2). So `resume_render_jobs()` and the semaphore run in 2 independent instances → double-increment confirmed in logs.
4. **Logs around the time:** only `[render] resuming … after restart` lines (several, doubled per job) plus two `[render] voice/video/pad` timing lines. No Traceback / "Killed" / timeout text in app logs — consistent with a kernel OOMKill (no Python traceback) rather than an application exception.

## Fixes
- **User (tier_upgrade_needed):** tier_0's 512Mi memory limit is the confirmed OOM ceiling. Raise the tier (Deployment Panel → Resources) so the render has headroom above 512Mi, then re-run a render.
- **Code (E1):**
  - Guard `resume_render_jobs()` so it does not run independently in every replica and does not blindly `$inc attempts` on every restart — e.g. an atomic claim / single-leader resume, or only increment on a genuine new user-initiated attempt. This stops crash-restarts and the 2nd replica from burning the retry budget and producing the false "2 baar" failure.
  - Reduce per-render peak memory (stream/scene-by-scene ffmpeg, lower thread/buffer use) so a single render fits a smaller footprint; and/or distinguish an OOM/crash failure from a genuine render error in the user-facing message.
