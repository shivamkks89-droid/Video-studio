# RCA — Play Store Kit "cannot be generated" (cinemaai.online / video-studio-ai-38)

## Problem statement
User: POST /api/studio/playstore-kit never finishes; kit stays generating/never completes. Preview works; curl to https://cinemaai.online/api/... returned HTTP 520.

## Verdict
The Play Store Kit **background task (`_kit_job`) is being OOM-killed mid-render on tier_0**. The pod dies by SIGKILL (OOMKilled, exit 137) during the PIL image compose + ffmpeg 15s MP4 build, which is heavier than the tier_0 **512Mi** memory limit allows. Because the kill is instant, the job's own `try/except` (which sets status `failed` + refunds 20 credits) never runs, so kit docs are frozen in `status:"rendering"` forever and credits are never refunded.

## Evidence
1. **Code is deployed (NOT a 404).** Backend logs show `POST /api/studio/playstore-kit` → `200 OK` and repeated polling `GET /api/studio/playstore-kit/<id>` → `200 OK`. Endpoint exists on the active run `08ca46bf…`.
2. **3 kit docs stuck in "rendering"** (`playstore_assets`, kind:"kit", app com.heartlink.app, user_61898e5d25fc), created 10:38:43, 10:41:49, 10:52:59 UTC. None have an `error` field; none reached `failed` or `complete`.
3. **No failure/traceback/refund anywhere in logs** (filtered playstore|kit|ffmpeg|scrape|Traceback|refund over 24h). If scrape (Play Store IP block), ffmpeg-missing, or any caught exception had occurred, `_kit_job`'s except would have written `failed` + refunded. It didn't → the process was killed before the handler could run.
4. **Pod OOMKilled, exit 137, restarts=3**, last_termination finished `2026-11-10T10:54:05Z` — aligns with the 10:52:59 kit's promo-build phase. `get_pod_events` kill_findings: `OOMKilled (exit 137) … restarts=3`.
5. **Tier_0 = Starter: memory 200Mi request / 512Mi limit, cpu 250m limit, replicas 2** (get_tier). In-process PIL composite of header+screenshots and an ffmpeg MP4 encode easily blows past 512Mi.
6. **Cloudflare 520** on `/api/` is a downstream symptom: when the origin pod is OOM-restarting/crash-looping (startup probe 503 / "connection refused" events observed), the Cloudflare worker gets no valid origin response → 520. Not a separate bug.

## Ruled out
- Play Store blocking prod IP / scrape failure — would produce a caught `failed`+refund record; none exist.
- ffmpeg binary missing — same; also no traceback.
- Not a routing/404 — endpoint returns 200.

## Secondary design fragility (contributes, worth fixing)
- `_kit_job` is an in-memory `asyncio.create_task`. With **2 replicas**, the task lives only in the pod that served the POST; any restart/OOM on that pod orphans the job with no recovery. There is no watchdog to reap stale "rendering" docs, so a lost task never refunds or fails out — it hangs until the 4-min client poll gives up, exactly the user's symptom.

## Recommended fixes
1. **Tier upgrade (User, Resources tab):** tier_0's 512Mi is the confirmed ceiling being hit (OOMKilled at limit). Raise to tier_1 (Launch) or higher to give the ffmpeg+PIL render headroom, then retry a kit.
2. **Code (E1):** make the render survivable and self-healing:
   - Run ffmpeg as an external subprocess (not in the API process) and cap memory/resolution/threads; process/stream screenshots one at a time and release PIL buffers (`img.close()`/del) between composites to flatten the peak.
   - Add a watchdog/TTL that marks any `kind:"kit"` doc stuck in `rendering` beyond the render budget as `failed` + refunds the 20 credits — so an OOM/pod-restart no longer freezes the kit or the user's credits.
   - Consider moving the heavy render off the request-serving pod (worker/job) given the 2-replica in-memory task design.
3. **Data (User / E1):** the 3 stuck docs (kit_11d77adc22e1, kit_7b55c45cd5c2, kit_0634c87df66a) should be marked `failed` and the 20 credits × 3 refunded to user_61898e5d25fc — they are charged but never delivered.

## Reproduction note
Not reproduced in an eph sandbox: the sandbox is granted more memory than the prod tier, so a tier_0 OOM will not reproduce there. Root cause is proven directly from the OOMKilled pod event + the stuck-rendering/no-refund DB+log state.
